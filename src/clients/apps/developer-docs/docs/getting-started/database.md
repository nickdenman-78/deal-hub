# The database

ETS uses one PostgreSQL database, `ets`, with **a schema per module** (`deals`, `users`, and in time `settlement`,
`risk`, …). Each module that uses EF Core owns its `DbContext` and its migrations, under `Persistence/Migrations`
in its Infrastructure project, with the migrations history table in its own schema. Marten (the Deals event store)
and Wolverine create their own tables. The reasoning is in ADR-0010,
`docs/architecture/adr/0010-persistence-conventions.md`.

The AppHost's PostgreSQL container starts empty. When the API starts in Development:

- **Users** applies its own migrations, then seeds the roles and users in `Users:DevelopmentSeed`.
- **Every other module** needs `dotnet ef database update` run by hand, after you add a migration and after the
  PostgreSQL container is recreated.

## Add a migration

Add a migration after changing a module's EF Core model. This only writes C# files; it never connects to the
database. `Persistence/Migrations` is generated by EF and never hand-edited.

::: code-group

```pwsh [PowerShell]
dotnet ef migrations add <Name> --project src\modules\deals\Ets.Modules.Deals.Infrastructure --context DealsDbContext --output-dir Persistence\Migrations
dotnet ef migrations add <Name> --project src\modules\users\Ets.Modules.Users.Infrastructure --context UsersDbContext --output-dir Persistence\Migrations
```

```bash [bash]
dotnet ef migrations add <Name> --project src/modules/deals/Ets.Modules.Deals.Infrastructure --context DealsDbContext --output-dir Persistence/Migrations
dotnet ef migrations add <Name> --project src/modules/users/Ets.Modules.Users.Infrastructure --context UsersDbContext --output-dir Persistence/Migrations
```

:::

## Apply migrations

`dotnet ef` builds each context through a design-time factory (`DealsDbContextFactory`, `UsersDbContextFactory`)
that reads the connection string `ConnectionStrings:ets` from these sources, later ones winning:

1. `appsettings.Migrations.json` in the Infrastructure project — committed, and with no password.
2. `appsettings.Migrations.local.json` beside it — git-ignored, for your real connection string.
3. The `ConnectionStrings__ets` environment variable — the same key the AppHost gives the API.

The API never reads these files. To apply migrations:

1. Start the AppHost and wait until PostgreSQL is running.
2. In the Aspire dashboard, open the `ets-api` resource and copy the value of its `ConnectionStrings__ets`
   environment variable.
3. Create `appsettings.Migrations.local.json` beside `appsettings.Migrations.json` in the module's Infrastructure
   project:

   ```json
   {
     "ConnectionStrings": {
       "ets": "<the value you copied>"
     }
   }
   ```

4. Run `database update` for the module:

   ::: code-group

   ```pwsh [PowerShell]
   dotnet ef database update --project src\modules\deals\Ets.Modules.Deals.Infrastructure --context DealsDbContext
   ```

   ```bash [bash]
   dotnet ef database update --project src/modules/deals/Ets.Modules.Deals.Infrastructure --context DealsDbContext
   ```

   :::

Instead of the local file you can set the `ConnectionStrings__ets` environment variable, or pass
`--connection "<connection string>"` to `database update`.

::: danger Never commit a password
A real connection string belongs only in `appsettings.Migrations.local.json` or your environment. The committed
`appsettings.Migrations.json` must not hold a password.
:::

## The PostgreSQL password

The AppHost does not set one. Aspire generates a random password on the first run and keeps it in the AppHost's
user secrets as `Parameters:postgres-password` — on Windows in
`%APPDATA%\Microsoft\UserSecrets\ets-aspire-apphost\secrets.json`, on macOS and Linux in
`~/.microsoft/usersecrets/ets-aspire-apphost/secrets.json`, never in the repository. The username is `postgres`.
To see it:

::: code-group

```pwsh [PowerShell]
dotnet user-secrets list --project src\aspire\Ets.Aspire.AppHost
```

```bash [bash]
dotnet user-secrets list --project src/aspire/Ets.Aspire.AppHost
```

:::

To choose your own, set it **before the container is first created**:

::: code-group

```pwsh [PowerShell]
dotnet user-secrets set "Parameters:postgres-password" "<password>" --project src\aspire\Ets.Aspire.AppHost
```

```bash [bash]
dotnet user-secrets set "Parameters:postgres-password" "<password>" --project src/aspire/Ets.Aspire.AppHost
```

:::

::: warning Changing it later loses your local data
The container is persistent and PostgreSQL reads the password only when its volume is initialised. Changing the
password afterwards means deleting the `postgres` container and its volume, and with them every local schema and
row. Re-apply the migrations afterwards.
:::

## Inspect the database

Connect any client (DataGrip, psql, …) to the `ets` database with the host, port, username and password from the
`ConnectionStrings__ets` value above. The port is the one the AppHost assigned, not necessarily `5432`.

::: tip DataGrip shows only `public`
DataGrip shows only the `public` schema until you tick the module schemas (`deals`, `users`, …) in the data
source's **Schemas** tab.
:::
