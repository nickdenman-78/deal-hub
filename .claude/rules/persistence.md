# Persistence & messaging infrastructure rules

Reasoning: ADR-0010 (PostgreSQL/EF Core), 0011 (Wolverine), 0013 (Marten), 0015 (Quartz).

## PostgreSQL / EF Core

- One `{Module}DbContext` per module, own schema, `UseSnakeCaseNamingConvention()`, migrations history table
  in that schema, deriving from `DbContextBase`.
- Use the shared `NpgsqlDataSource` from Aspire; never build connection strings by hand.
- Maps are `{Entity}Map : IEntityTypeConfiguration<…>` under the context's `Persistence/Configuration`
  namespace; `OnModelCreating` only sets the schema and calls `ApplyAllConfigurations<TContext>()`.
- Enums stored as member-name strings via the context convention. Every column has `HasColumnOrder`.
- Ids are Guid v7 generated by the domain — configure keys with `ValueGeneratedNever()`.
- `timestamptz` for instants, `date` for trading days; `jsonb` only for data never filtered on.
- Repositories reconcile child collections by id — never clear and rebuild.
- `ISoftDelete` requires a global query filter before any entity adopts it.
- Reads: `AsNoTracking()` projections; Dapper allowed for reporting/risk SQL in the module's own schema.
- `Persistence/Migrations` is EF-generated: never hand-edit it. Never read another module's schema.

## Marten (Deals, Settlement)

- One ancillary store per module (`IDealsStore`), own schema; stream id = aggregate id.
- Append with the expected version; map concurrency failures to `DomainError.Conflict`.
- Never change a released event type; add a new type and an upcaster.
- Inline projections only for state the write side needs; everything else is an async projection.

## Wolverine

- Consumers live in `Infrastructure/Messaging`, translate the integration event into this module's command,
  and call the kernel handler. Business failures → `BusinessRuleViolationException` (dead-lettered, no retry).
- The unit of work saves state and flushes mapped integration events through the outbox in one transaction
  (`IDbContextOutbox<T>.SaveChangesAndFlushMessagesAsync()` or the Marten–Wolverine session).
- Integration event types come from the producer's IntegrationEvents project; never define one here.
- Never call RabbitMQ.Client directly.

## Quartz

- A job only sends a Wolverine command carrying its business date. Schedules come from options, not code.
